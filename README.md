# public-repo-audit

개인 개발 프로젝트를 GitHub에 **공개하기 직전**, 비밀정보·개인정보 노출과 문서 누락을 같은 순서로 점검하고 중요도별 보고서를 만들어 주는 Claude Code 스킬입니다.

```
my-skills/
├── README.md
└── .claude/
    └── skills/
        └── public-repo-audit/
            └── SKILL.md
```

## 1. 기존의 반복적인 불편

교육 과정에서 Todo 앱, Safety Action Tracker 같은 프로젝트를 만들 때마다 마지막 단계는 항상 "GitHub에 올려도 되나?" 확인이었습니다. 그때마다 이런 일을 기억에 의존해 반복했습니다.

- `.env`가 정말 `.gitignore`에 들어갔는지, 이미 커밋된 적은 없는지 매번 다시 확인
- Supabase 키처럼 **공개해도 되는 키**와 **절대 공개하면 안 되는 키**(service_role 등)를 손으로 구분
- 테스트 데이터의 이메일·전화번호가 가짜인지, 문서에 로컬 경로나 실명이 남아 있지 않은지 눈으로 훑기
- README에 설치·실행 방법이 빠져 있다는 것을 공개한 **뒤에야** 발견
- AI에게 "올려도 돼?"라고 물으면 매번 점검 항목이 달라지고, 확인하는 과정에서 **실제 키 값이 대화창에 그대로 출력**되기도 함

즉, 점검 항목은 거의 같은데 순서와 범위가 매번 달랐고, 빠뜨린 항목이 있어도 알 수 없었습니다.

## 2. 이 스킬을 만든 이유

- 반복되는 점검을 **고정된 7단계 절차**로 만들어 빠뜨리는 항목을 없애기 위해
- 점검 중 **비밀 값이 화면에 출력되지 않도록** 명령 자체를 파일명·개수·마스킹 출력으로 제한하기 위해
- 점검 도구가 마음대로 파일을 지우거나 커밋·푸시·이력 재작성을 하지 않도록 **읽기 전용 + 승인 후 조치** 원칙을 강제하기 위해
- "비밀정보 없음"이라는 과신 대신 **검사 범위와 한계를 매번 보고서에 명시**하기 위해

## 3. 스킬을 사용하면 무엇이 달라지는가

| 이전 | 이후 |
|---|---|
| 기억에 의존한 점검, 매번 다른 항목 | Git 상태 → 비밀/개인정보 → .gitignore → README → 커밋 예정 변경 → 위험 분류 → 보고서의 고정 순서 |
| 현재 파일만 확인 | 현재 추적 파일 + **Git 이력** + 스테이징/미추적/미푸시 변경까지 확인 |
| 키 값이 대화에 노출될 위험 | `git grep -l`, 개수 집계, `앞 4자 + ****` 마스킹만 사용 |
| "괜찮은 것 같다" 수준의 결론 | 🔴 Critical / 🟠 High / 🟡 Medium / 🔵 Low / ✅ 확인됨 등급과 권장 조치 표 |
| 발견 즉시 수정·삭제 | 조치는 "승인이 필요한 다음 조치" 체크리스트로만 제안 |

## 4. 설치 경로와 방법

Claude Code는 프로젝트의 `.claude/skills/<스킬이름>/SKILL.md`를 프로젝트 스킬로 인식합니다.

**특정 프로젝트에만 설치** (점검할 프로젝트 루트에서):

```bash
mkdir -p .claude/skills/public-repo-audit
```

```bash
cp <my-skills 경로>/.claude/skills/public-repo-audit/SKILL.md .claude/skills/public-repo-audit/
```

**모든 프로젝트에서 사용** (사용자 전역 스킬):

```bash
mkdir -p ~/.claude/skills/public-repo-audit && cp <my-skills 경로>/.claude/skills/public-repo-audit/SKILL.md ~/.claude/skills/public-repo-audit/
```

설치 후에는 **새 Claude Code 대화**를 열어야 스킬 목록에 반영됩니다.

> 참고: 대상 프로젝트의 `.gitignore`에 `.claude/`가 있으면 복사한 스킬 파일은 Git에 올라가지 않습니다(로컬 도구로만 사용). 스킬을 저장소에 함께 공개하고 싶다면 `.gitignore`를 직접 조정해야 합니다.

## 5. 한 문장 호출 예시

점검할 프로젝트 루트에서 Claude Code를 열고:

```
공개 저장소 점검해 줘.
```

`description`에 다음과 같은 표현이 모두 들어 있어 비슷한 요청에도 연결되도록 했습니다.
"GitHub 올리기 전에 확인해 줘", "개인정보 노출 여부 점검해 줘", ".env 커밋됐는지 확인해 줘", "public으로 바꿔도 되는지 봐 줘", "audit this repo before making it public".
반대로 일반 코드 리뷰·버그 점검 요청에는 사용하지 않도록 범위를 적어 두었습니다.

자연어로 연결되지 않으면 명시적으로 호출합니다.

```
/public-repo-audit
```

## 6. 실제 테스트 과정과 확인 결과

테스트 대상: 교육 과정에서 만든 Safety Action Tracker(FastAPI + Supabase, 이미 GitHub에 공개되어 있는 저장소). 대상 프로젝트의 코드와 Git 이력은 수정하지 않았습니다.

### 6-1. 설치 확인 — ✅ 수행함

- `SKILL.md`를 대상 프로젝트의 `.claude/skills/public-repo-audit/`에 복사하고 원본과 바이트 단위로 동일함을 확인(`cmp`).
- 복사 후 대상 저장소의 `git status --short` 결과가 비어 있음을 확인 → 대상 프로젝트의 Git 상태는 변하지 않음(`.claude/`가 ignore 대상).

### 6-2. 점검 절차 드라이런 — ✅ 수행함 (스킬 작성 세션에서 절차의 명령을 직접 실행)

| 단계 | 결과 |
|---|---|
| 1. Git 상태 | `main`, 원격과 동기화, 미커밋 변경 없음, 추적 파일 34개, 이력 커밋 4개 |
| 2. 비밀/개인정보 | 키·토큰 형태 패턴 0건 / 연결 문자열 비밀번호 0건 / JWT 형태 이력 0건 / 휴대전화·주민번호 형태 0건 / 이메일 24건 모두 `example.com` 도메인 / 로컬 사용자 경로 0건 / 이력의 `service_role` 11건은 모두 "사용하지 않는다"는 **설명 문구**(키 값 아님) |
| 2. 하드코딩 의심 | 13줄 검출 → 모두 `token = request.cookies.get(...)` 같은 변수 대입 또는 테스트용 더미 문자열(오탐) |
| 3. .gitignore | `.env`, `.venv/`, `.pytest_cache/` 정상 ignore 확인, "ignore 대상인데 추적 중인 파일" 0건. `.env.example`은 비밀 값이 비어 있고 데모 이메일만 `example.com` |
| 4. README | 프로젝트 설명 ✅, 설치 방법 ✅, 실행 방법 ✅, 환경변수 안내 ✅, 배포 방법 ✅, **LICENSE 파일 없음** ❌ |
| 5. 커밋 예정 변경 | 스테이징 0 / 수정 0 / 미추적 0 / 미푸시 커밋 0 |
| 6. 분류 | 🔴 0, 🟠 0, 🟡 1 (라이선스 없음), 🔵 0, 배포 URL 공개는 의도된 정보로 ✅ |

드라이런에서 **스킬 자체의 버그를 하나 발견해 고쳤습니다.** 처음 작성한 마스킹 명령이 `git grep -n` 출력의 `파일:줄번호:` 콜론을 값 구분자로 잘못 인식해, 실제 값 대신 줄 앞부분을 가리고 있었습니다. 키워드(`password`, `token` 등) 바로 뒤의 값만 가리도록 정규식을 수정했고, 가짜 키 `API_KEY = "sk-abc..."` 입력이 `API_KEY = "sk-a****"`로 출력되는 것을 확인했습니다.

### 6-3. 별도 대화에서 한 문장 호출 검증 — ✅ 수행함

스킬 작성 대화와 분리된 **새 Claude Code 대화**에서 확인했습니다.

1. 대상 프로젝트 폴더를 작업 폴더로 새 Claude Code 대화를 열었습니다.
2. `공개 저장소 점검해 줘.` 한 문장만 입력했습니다. 슬래시 명령은 사용하지 않았습니다.
3. 아래 항목을 확인했습니다.

| 확인 항목 | 결과 |
|---|---|
| 자연어 한 문장으로 스킬 자동 선택 | ✅ `공개 저장소 점검해 줘.` 입력만으로 실행됨 (명시 호출 불필요) |
| 7단계 형식 보고서 출력 | ✅ 결론 → 발견 사항 표 → 단계별 결과 → 검사 범위와 한계 → 승인이 필요한 다음 조치 순서로 출력 |
| 비밀 값 미출력 | ✅ 위치(`파일:줄`)와 근거만 표기, 키·비밀번호 값은 출력되지 않음 |
| 한계 명시 | ✅ "이번 패턴 검사에서는 발견되지 않음"으로 표현하고, 비밀정보 부재를 보장하지 않는다고 명시 |
| 승인 없는 수정·커밋 없음 | ✅ "점검만 했고 파일은 하나도 바꾸지 않았습니다"로 종료, 조치는 체크리스트로만 제안 |

새 대화에서 나온 점검 결과 요약:

| 등급 | 항목 | 권장 조치 |
|---|---|---|
| 🟡 Medium | LICENSE 파일 없음 | 원하는 라이선스 파일 추가 |
| 🔵 Low | `.gitignore`에 `.env`만 있고 `.env.local`, `.env.production` 같은 변형은 막지 못함 | `.env.*`와 `!.env.example` 추가 |
| ✅ 확인됨 | `.env`는 ignore 되고 이력에 추가된 적 없음, 관리자 키 미사용, 배포 설정의 비밀 값은 `sync: false`, 이메일은 모두 예시 도메인이고 커밋 작성자 이메일은 noreply 주소 | — |

`.env.*` 누락은 6-2 드라이런에서 놓쳤던 항목인데, 새 대화에서 스킬이 3단계(.gitignore 검토) 기준에 따라 찾아냈습니다. 권장 조치 두 가지는 아직 승인하지 않았으며, 대상 프로젝트는 수정되지 않았습니다.

## 7. 스킬의 한계

- **모든 비밀정보를 찾지 못합니다.** 정규식과 파일명 규칙 기반이라 형태가 일정하지 않은 비밀번호, 인코딩·분할된 값, 이미지·PDF·바이너리 내부, 서브모듈, Git LFS 객체는 놓칠 수 있습니다.
- GitHub 쪽 데이터(이슈, PR, Actions 로그, 포크, 이미 생성된 캐시)는 검사하지 않습니다.
- 이메일·전화번호가 실제 개인정보인지 시연 데이터인지는 최종적으로 사람이 판단해야 합니다.
- 이미 공개된 저장소에서 키가 발견되면 이력을 지워도 노출은 되돌릴 수 없습니다. 이 스킬은 **키 폐기·재발급**을 권고할 뿐 직접 하지 않습니다.
- 이력 전체 검사(`git log -p`)는 큰 저장소에서 느릴 수 있어 범위를 줄일 수 있으며, 그 경우 보고서에 명시합니다.
- 명령은 Git Bash 기준으로 작성했습니다. 다른 셸에서는 Claude가 같은 의미의 명령으로 바꿔 실행해야 합니다.
- `gitleaks`, `trufflehog` 같은 전용 도구를 대체하지 않습니다. 설치되어 있으면 함께 쓰기를 권합니다.
